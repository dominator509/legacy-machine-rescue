# Requirements Document

## Introduction

Legacy Machine Rescue currently supports raw disk images and fixed VHD images (with footer stripped). This feature adds support for reading Microsoft Virtual Hard Disk (VHD) format files with dynamic allocation. Dynamic VHDs use a sparse allocation format where only used sectors are stored in data blocks, with a Block Allocation Table (BAT) tracking block locations and a sector bitmap tracking used sectors within each block. The feature must preserve existing raw and fixed VHD support while adding dynamic VHD reading capability.

## Glossary

- **VHD_Reader**: The component that parses VHD container formats and extracts flat disk bytes for filesystem analysis
- **VHD_Footer**: The 512-byte VHD footer structure at the end of VHD files containing format metadata
- **VHD_Header**: The 1024-byte VHD header structure in dynamic/differencing VHDs containing BAT and block information
- **BAT**: Block Allocation Table - a table of block offsets within the VHD file
- **Sector_Bitmap**: Bitmap tracking which sectors within a block contain data (1 = data present, 0 = sparse/zero-filled)
- **Data_Block**: A contiguous region of sector data stored in the VHD file
- **Flat_Disk_Bytes**: The complete disk image as it would appear to emulator and filesystem code, with sparse regions expanded to zeros
- **Fat12_Image**: Synthetic test image generated by the fixtures module
- **Corruption_Generator**: Test component that modifies bytes to create invalid/corrupted VHD files
- **Synthetic_Builder**: Test helper that wraps valid fat12_image content in VHD container format

## Requirements

### Requirement 1: Parse Dynamic VHD Container Format

**User Story:** As a machine shop technician, I want to analyze dynamic VHD disk images directly, so that I can inspect legacy CNC machine disks without converting them to raw format first.

#### Acceptance Criteria

1. WHEN a valid dynamic VHD file is provided, THE VHD_Reader SHALL parse the VHD footer, header, BAT, and sector bitmaps to reconstruct flat disk bytes
2. WHERE the VHD container is a fixed VHD, THE VHD_Reader SHALL preserve the existing behavior (strip footer, return raw data)
3. WHERE the VHD container is a raw image, THE VHD_Reader SHALL preserve the existing behavior (return raw data unchanged)
4. FOR ALL valid dynamic VHD images, THE VHD_Reader SHALL produce flat disk bytes identical to the equivalent raw disk content (excluding VHD container metadata)

### Requirement 2: Validate VHD Structure Before Memory Allocation

**User Story:** As a software developer, I want the VHD reader to validate structure integrity before large memory allocations, so that malicious or corrupted files don't cause excessive memory usage or crashes.

#### Acceptance Criteria

1. WHEN the VHD footer signature is invalid, THE VHD_Reader SHALL validate the footer record within its 512-byte span (checking both trailing footer and potential leading backup footer positions as applicable) and raise ValueError with a clear message. Raw detection for non-VHD images SHALL remain unchanged. Recognition of raw vs fixed vs dynamic VHD SHALL preserve the existing detection algorithm's behavior and output, and strict footer/header validation SHALL apply only after a VHD container is recognized as dynamic type. Bad signatures on arbitrary raw data SHALL NOT cause misclassification or rejection of valid raw images.
2. WHEN the VHD header is truncated or corrupted, THE VHD_Reader SHALL validate header structure before accessing referenced data blocks and raise ValueError with a clear message
3. WHERE block size is invalid (non-positive, not power-of-two, not sector-aligned, or exceeds an explicit bound defined in the design document), THE VHD_Reader SHALL raise ValueError before allocation. The design SHALL specify an explicit maximum block size consistent with the 256 MiB virtual size cap.
4. WHERE dynamic VHD virtual disk size exceeds 256 MiB, THE VHD_Reader SHALL raise ValueError before allocation (exactly 256 MiB is allowed). This cap applies only to dynamic VHDs; fixed VHD and raw images SHALL not be limited by this constraint.
5. WHEN BAT entries reference out-of-range file offsets or invalid block alignments, THE VHD_Reader SHALL validate all offset and length arithmetic before reading and raise ValueError
6. FOR ALL dynamic VHD inputs, THE VHD_Reader SHALL validate footer checksum, header checksum, disk type (type 3 dynamic), explicitly reject type 4 differencing, and verify table capacity matches virtual size before flattening operations. This strict validation SHALL apply ONLY to the dynamic VHD path; fixed VHD (type 2) processing SHALL retain its existing validation behavior and output identical results to current implementation.

### Requirement 3: Handle Sparse Data Blocks Correctly

**User Story:** As a filesystem analyzer, I want sparse regions in dynamic VHDs to appear as zero-filled sectors, so that partition tables and filesystems can be detected consistently.

#### Acceptance Criteria

1. WHERE sector bitmap indicates a sector is unused (0), THE VHD_Reader SHALL fill the corresponding 512-byte sector with zeros in the flat disk bytes output
2. WHERE sector bitmap indicates a sector is used (1), THE VHD_Reader SHALL copy the corresponding 512-byte sector from the data block to the flat disk bytes output
3. FOR ALL dynamic VHD images, THE VHD_Reader SHALL produce flat disk bytes where unused sectors are exactly zero (0x00)
4. FOR ALL dynamic VHD images, partitions() and volumes() functions SHALL return identical results to equivalent raw images (excluding container metadata differences)

### Requirement 4: Maintain Backward Compatibility

**User Story:** As an existing user, I want raw and fixed VHD support to remain unchanged, so that my existing workflows continue to work without modification.

#### Acceptance Criteria

1. WHEN processing raw images, THE image.load function SHALL return identical data and info dictionary as the current implementation
2. WHEN processing fixed VHD images, THE image.load function SHALL strip the 512-byte footer and return identical data and info dictionary as the current implementation
3. WHEN processing dynamic VHD images, THE image.load function SHALL include "dynamic VHD" in the info dictionary's container field
4. FOR ALL supported image types, THE inventory module SHALL produce identical inventory results (excluding container metadata fields)

### Requirement 5: Test with Synthetic VHD Generation

**User Story:** As a test developer, I want to generate synthetic dynamic VHDs for testing without external downloads, so that tests are reproducible and don't rely on external resources.

#### Acceptance Criteria

1. THE Synthetic_Builder SHALL wrap valid fat12_image content in dynamic VHD container format for testing
2. FOR ALL synthetic dynamic VHDs, parsing then extracting SHALL produce identical flat disk bytes to the original fat12_image
3. WHERE deliberate corruption is applied to VHD structures (invalid/truncated footer/header/BAT), THE VHD_Reader SHALL raise ValueError as specified in Requirement 2
4. FOR 100 deterministic mutation test iterations using standard library deterministic randomization, WHERE mutations produce valid VHDs, THE VHD_Reader SHALL succeed; WHERE mutations produce invalid VHDs, THE VHD_Reader SHALL raise ValueError; THE VHD_Reader SHALL never crash with unexpected exceptions or hang

### Requirement 6: Document Implementation Constraints

**User Story:** As a project maintainer, I want clear implementation constraints documented, so that future developers understand the design boundaries.

#### Acceptance Criteria

1. THE implementation SHALL use Python 3.8+ standard library only (no pip installs, no external property-testing libraries)
2. THE implementation SHALL handle all parsing errors with ValueError (no crashes)
3. THE implementation SHALL include both unit tests and property-based tests using standard library deterministic randomization
4. THE implementation SHALL NOT support VHD differencing disks (parent/child chains)
5. THE implementation SHALL NOT modify the VHD file (read-only operation)
6. ALL code and tests SHALL be authored by Kiro with commit author "DSW Enterprises"
7. ALL claims about functionality SHALL be labelled MEASURED, EMULATOR, or NOT PROVEN per product honesty rules
